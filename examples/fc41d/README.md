# ESPHome on the B2500's own Wi-Fi module

**Experimental, untested on a real battery.**

The B2500 talks to the cloud and the Marstek app through a Quectel FC41D
Wi-Fi/BLE module (a Beken BK7231N) driven by the battery's main MCU over AT
commands. These configs replace the module's firmware with ESPHome, so the
battery needs no external ESP32: it shows up in Home Assistant directly.

| File | What it is |
|---|---|
| `ble-spike.yaml` | BLE test for the FC41D-TE-B eval kit: the battery's `FF00` service, echoing `ff01` writes on `ff02` under Wi-Fi load. |
| `b2500-module.yaml` | The module firmware: answers the battery MCU (`hame_at`), keeps the app's Bluetooth service, forwards the battery's MQTT session to the Hame cloud (switchable, on by default), and shows the battery in Home Assistant (`hame_device` with the B2500 v2 profile). |
| `devices/` | Device profiles: what a Marstek device's status keys mean and how it is controlled (see below). |

Components (in `components/`):

- `bk72xx_ble_server`: BLE GATT server (peripheral) for the BK7231N, on
  top of esphome's `bk72xx_ble`. `mac_address:` sets the public BLE address
  (the stock module's own one is in its config sector; ESPHome would
  otherwise use the Wi-Fi MAC + 1).
- `hame_at`: the AT firmware emulator. It covers system, Wi-Fi, BLE, MQTT,
  certificate upload, HTTP and TCP/UDP sockets (the CT and Shelly meter
  path). Optional cloud forwarding uses the broker, credentials and
  certificates the battery MCU sends. Formats and timing follow the hm2500
  firmware emulator, which runs the real MCU images against a module model.
  Host-tested in `tests/hame_at`.
- `hame_device`: a Marstek device described in YAML. It reads the device's
  status messages (`key=value,...`), keeps every key's latest value and sends
  `cd=...` commands from templates. It knows nothing about a particular
  device: the profiles in `devices/` do. Host-tested in `tests/hame_device`.

## Home Assistant entities

`b2500-module.yaml` defines a `hame_device` hub on the battery's MQTT session
and includes the B2500 v2 profile, which adds the battery's message types and
about 85 entities: state of charge, PV and output power, temperatures, daily
energy, CT readings, pack status, and the settings (charging mode, adaptive
mode, discharge depth, CT phase, surplus feed-in, the five schedule periods).
Field meanings and commands follow [hm2mqtt](https://github.com/tomquist/hm2mqtt).

| Profile | Adds | Request |
|---|---|---|
| `devices/b2500-v2.yaml` | status, settings, schedule, CT diagnosis | `cd=1` every 60 s, `cd=28` every 5 min |
| `devices/b2500-v2-electrical.yaml` | input, output and battery voltages and currents | `cd=16` every 60 s |
| `devices/b2500-v2-cells.yaml` | cell voltages per pack, min/max/average/spread | `cd=13` every 60 s |

The add-ons are off by default: each costs about 5 KB of RAM, which the TLS
connection to the cloud needs. The profiles are generated by
`tools/gen_b2500_profiles.py`; edit that, not the YAML.

### Adding a device

A profile is an ESPHome package that extends a hub you define (keep the list
form, `- id:`, which `!extend` needs):

```yaml
hame_device:
  - id: battery
    hame_at_id: module   # the transport; others can feed the hub too

packages:
  b2500: !include {file: devices/b2500-v2.yaml, vars: {device: battery}}
```

The profile declares the device's message types (recognised by their keys,
each with its poll request) and maps keys to entities:

```yaml
hame_device:
  - id: !extend ${device}
    messages:
      - name: runtime
        required_keys: [pe, kn, do]   # a message with all of these is "runtime"
        poll: "cd=1"
        interval: 60s

sensor:
  - platform: hame_device
    hame_device_id: ${device}
    name: Battery Percentage
    key: pe
    valid_min: 0          # values outside are dropped (no-reading sentinels)
    valid_max: 100
    unit_of_measurement: "%"

select:
  - platform: hame_device
    hame_device_id: ${device}
    name: Charging Mode
    key: cs
    command: "cd=17,md={value}"
    options: {"0": Simultaneous, "1": Fully Charge Then Discharge}
```

Entities: `sensor` (one key, a bit range, or several keys combined as
sum/min/max/average/spread; `multiply`, `monotonic` for daily counters),
`binary_sensor` (`bit` or `on_values`), `text_sensor` (`map`, `default`,
`time`), `number`, `select`, `switch` (`command`, or `command_on`/`_off`),
`text` (`time` for schedule times), `button`. `message:` binds an entity to
a message type (default: the first); devices reuse keys across types.

Command templates: `{value}` is the new value, `{key}` the device's current
value of a key (so a setting can resend the others, like the schedule),
`{key|default}` with a fallback, and `[...]` an optional section that is left
out when a key in it is unknown. `hame_device.send_command` and
`hame_device.poll` are available as actions, `on_message`/`on_command` as
triggers.

## Cloud access

The battery's traffic to the Hame cloud can be passed through or answered on
the module itself, the way [Marsrelay](https://github.com/tomquist/marsrelay)
does.

- **Master switch.** `cloud:` (also a switch in Home Assistant) turns all
  cloud access on or off. Off means everything is answered on the module, and
  the Marstek app then only works over Bluetooth.
- **Per kind of traffic.** While cloud access is on, `cloud_access:` decides
  for each kind of traffic:

| Key | Covers | Default |
|---|---|---|
| `mqtt` | the battery's broker session: app control, cloud data | `forward` |
| `time` | the battery's clock request | `auto` |
| `device_config` | output limits, SOC, schedules, weather | `auto` |
| `reports` | statistics and error uploads | `forward` |

- **Modes.** `forward` passes the traffic through. `local` answers on the
  module. `auto` passes through and answers locally when the cloud fails
  (HTTP only).
- **Not covered by these settings:**
  - Requests to devices on your network (CT, P1 and Shelly meters) always go
    out.
  - Battery firmware downloads are blocked unless `allow_mcu_ota: true`.

## Bench testing on the eval kit

On the FC41D-TE-B, J201 (M_UART_USB) is the module's main UART (the battery
MCU's side, also used for flashing) and J202 (DEBUG_USB) is the debug UART
(ESPHome logs). On macOS the ports are `/dev/cu.usbserial-…`, on Linux
`/dev/ttyUSB<n>`; `python3 tools/fc41d_probe.py --list` shows them.
`ltchiptool` flashes only the app partition from the UF2, so the module's
bootloader stays; `ltchiptool flash write fc41d-stock.bin` restores the full
backup.

1. Back up the stock firmware. Start the command, then press SW301 when it
   waits for the chip:

   ```bash
   ltchiptool flash read bk7231n fc41d-stock.bin
   ```

2. Create `secrets.yaml` with `wifi_ssid` and `wifi_password`, then build and
   flash:

   ```bash
   esphome compile b2500-module.yaml
   ```

   ```bash
   ltchiptool flash write .esphome/build/b2500-module/.pioenvs/b2500-module/firmware.uf2
   ```

   For `ble-spike.yaml`, check the BLE link from a computer with Bluetooth
   (`pip install bleak`); `--duration 3600` keeps reconnecting for an hour:

   ```bash
   python3 ../../tools/ble_spike_check.py
   ```

3. Play the battery on J201. The simulator answers the profile's requests
   and applies its settings commands like a B2500, so every control can be
   tried from Home Assistant:

   ```bash
   python3 ../../tools/fc41d_mcu_sim.py /dev/cu.usbserial-XXXX
   ```

   Add `--broker host:8883 --ca ca.pem --cert client.pem --key client.key` to
   test cloud forwarding against your own TLS broker.

## Known limits

- **Flash.** `b2500-module.yaml` uses about 88% of the app partition (90%
  with both add-on profiles).
- **RAM.** On the eval kit about 50 KB of heap stay free with BLE and the
  API; the B2500 profile takes roughly 9 KB of that. RAM use with the cloud's
  TLS session open still has to be measured on hardware.
- **B2500 profile gaps.** Not ported from hm2mqtt yet: meter type/MAC
  setting, time zone, the "use flash commands" switch (the non-flash command
  codes are used), hiding the pass-through sensors on the HMJ, and the
  firmware-version checks for surplus feed-in and the CT phase.
- **TLS to the cloud.** `hame_at` runs mbedTLS itself (the SDK's 2.6) and
  enables ECDHE-RSA, AES-GCM and SNI, which the SDK leaves off. The SDK's
  config still limits it to RSA keys up to 3072 bits and SHA-1/SHA-256
  signatures (no ECDSA, no SHA-384): enough for Hame's AWS endpoint (Amazon
  Root CA 1, RSA 2048), not for chains such as Let's Encrypt's ISRG Root X1
  (RSA 4096). Tested against broker.emqx.io:8883. The handshake briefly
  takes the free heap down to about 10 KB.
- **Battery firmware updates.** These are blocked unless `allow_mcu_ota: true`.
- **Wi-Fi provisioning.** Setting Wi-Fi from the Marstek app is ignored.
  ESPHome manages Wi-Fi instead.
